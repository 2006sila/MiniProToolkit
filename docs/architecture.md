## MVP

```text
MiniProToolkit.App
  MainWindow / TaskbarStatusWindow
        |
        v
MiniProToolkit.Hardware
  PowerSwitchHardware
        |
        v
root\\WMI: PowerSwitchInterface
        |
        v
ACPI / EC firmware

MiniProToolkit.Guardian
  lease monitor -> recovery coordinator -> PowerSwitchHardware.RestoreAutomatic
```

`MiniProToolkit.Core` contains hardware-neutral snapshots, enums, the validated fan curve engine, and the failure-recovery controller. The WMI layer is isolated in `MiniProToolkit.Hardware`, so curve policy does not call WMI directly. CPU package power is read-only from Windows `Energy Meter` performance counters (prefer the `*_PKG` RAPL instance); it is reported in watts, recorded with telemetry, and remains unavailable (`null`) when the OS/firmware does not expose a valid counter. This is CPU package power, not total laptop/system wall power.

## Scope boundary (single-device product)

The current product supports **one controlled fan (Fan1), one calibration set, and one display with one taskbar/OSD/system-indicator configuration**. Fan2/RPM fields that may exist in hardware snapshots are read-only compatibility data and do not add a second control path. Multi-fan coordination, Fan2 selection, multi-set calibration, secondary-taskbar layouts, per-display settings and cross-screen/multi-display OSD are historical/product-plan references outside the current product scope, not release blockers, backlog items or acceptance items.

For the supported device, current-display DPI, Explorer re-attachment, taskbar relocation and sleep/resume remain valid target-machine acceptance items.

These are **not** planned, not implemented and not acceptance items, and they must not reappear as backlog entries:

- network upload/download rate and today's traffic (no collection, display or recording, not even hidden);
- keyboard backlight brightness/lighting mode (no read, no write). The `CanReadKeyboardBacklight` / `CanWriteKeyboardBacklight` flags in `HardwareCapabilities` / `HardwareCapabilityProbe` remain read-only capability detection only;
- vendor Fn key events and touchpad control (no research, no implementation). The app's own Windows global hotkeys (`Ctrl+Alt+1/2/3/A/F`) are implemented, are a different mechanism, and are **not** excluded - they must not be described as a vendor Fn replacement.

**Implemented and covered by Core unit tests, but not yet accepted on a target machine** (earlier documentation said they were still being developed, which no longer matches the source; they are neither "fully done" nor "plan only"): the RPM/s rate limit with its sticky sampling-window anchor (`FanCurve.cs`, `RpmRateLimit` still defaults to `null` and stays opt-in), the calibrated curve RPM feedback (`FanCurveSettings.RpmFeedback`, default-off and able only to increase duty) and curve 90 °C latch (`LatchCurveEmergency`, default-off, so old curve files keep the curve-only behaviour), the cross-process short-held lease lock plus compare-and-clear (`GuardianLease.cs`), the event-driven taskbar appbar refresh (`TaskbarRefreshPolicy.cs` plus the `TaskbarCreated`/`WM_DISPLAYCHANGE`/`WM_DPICHANGED`/`WM_SETTINGCHANGE` hook, while the displayed values still come from the 1 s sampling pass), the taskbar double-click compatibility rule (`TaskbarClickGesture`, double click = single click), the configurable OSD appearance (`OsdAppearance`, free hex colours and arbitrary font family), the runtime-only automation status board (`ProfileAutomationStatusBoard`) and the scripted-command request-id dedupe with its 45 s client answer budget (plus the packaging scripts' `<lease>.lock`). Each has unit tests (`FanCurveRpmRateLimitTests`, `FanCurveRpmFeedbackTests`, `FanCurveEmergencyLatchTests`, `GuardianLeaseTests`, `TaskbarRefreshPolicyTests`, `TaskbarClickGestureTests`, `OsdAppearanceTests`, `ProfileAutomationStatusTests`) and no comprehensive target-machine acceptance; limited snapshot-specific smoke does not accept every mechanism. The implemented behaviour is described in the taskbar, hardware-contract and scheduling sections below.

## Optional LibreHardwareMonitor cross-check (read-only)

A second, optional CPU measurement runs alongside the EC and Energy Meter readings purely for comparison. It is implemented in `MiniProToolkit.Hardware/LibreHardwareMonitorCpuSensor.cs` plus the hardware-neutral selection rules in `MiniProToolkit.Core/LibreHardwareMonitorSensorSelection.cs`. This CPU reader is separate from the optional GPU-only LHM reader described below; the project is not CPU-only.

| Source | Field | Meaning |
| --- | --- | --- |
| EC `GetHwTemp(HwTempType=1)` | `CpuTemperatureC` (unchanged) | Firmware/EC CPU temperature, integer Celsius. Still the only value used by the curve, fixed-RPM control, Guardian and safety thresholds. |
| Windows Energy Meter | `CpuPackagePowerWatts` (unchanged) | RAPL-style CPU package power estimate in watts. Not wall power. |
| LibreHardwareMonitor | `LhmCpuPackageTemperatureC` | CPU package temperature reported through LHM's own sensor stack. Same physical package as the EC value but read through a different path, so a few degrees of offset is normal. |
| LibreHardwareMonitor | `LhmCpuPackagePowerWatts` | LHM CPU package power sensor (usually MSR/RAPL backed). Not wall power and not comparable to a watt-meter reading. |
| LibreHardwareMonitor | `LhmStatus` | Short path-redacted state; diagnostic only. |

Selection rules (ThinkBookToolkit-style priority, reimplemented from the public behavior, no code copied): temperature prefers `CPU Package`/`Package`, then `Core Max`, `CPU Core`, `Tctl`, `Tdie`; package power accepts only `CPU Package`/`Package` and never falls back to a GPU, board or PSU sensor. Both passes match names case-insensitively, prefer exact matches, drop `null`/NaN/infinite values, and clamp plausibility to (0, 150] °C and (0, 1000] W while keeping one decimal place. The temperature floor is exclusive on purpose: without its optional kernel driver LibreHardwareMonitor still enumerates CPU temperature sensors but reports exactly 0.0 °C, and a live CPU never measures 0 °C, so such a value is treated as unavailable instead of being displayed as a healthy cross-check reading.

Operational behavior:

- The `LibreHardwareMonitorCpuSensor` instance is created in the `MainWindow` constructor (constructor only: it allocates a lightweight object and touches no driver); `Computer.Open()` happens on the app's existing one-second background sampling pass, never on the UI thread. It is a single instance guarded by a lock. In demo mode the field stays `null`, so nothing is opened or sampled.
- Only the CPU group is enabled (`IsCpuEnabled`) in this CPU reader; the separate `LibreHardwareMonitorGpuSensor` reader enables only the GPU group. In the CPU reader, GPU/NVAPI, motherboard, storage, network, controller, battery, PSU and power-monitor groups stay disabled. `Computer.Close()` runs on dispose.
- It never installs PawnIO, never issues MSR/MMIO writes, and never calls fan or EC control APIs. `PawnIo.IsInstalled` is only queried read-only to explain a missing sensor in `LhmStatus`.
- Any open/update failure, missing driver or missing sensor becomes an unavailable reading with a status string instead of an exception, so WMI and Energy Meter failures stay independent. The same applies to driver-less placeholder values: a rejected 0.0 °C / 0 W sensor stays empty and the status names the reason plus the missing-PawnIO hint, so a missing driver is never reported as a working cross-check.
- Failures are cached with a backoff computed as base delay × consecutive failures, capped at 5×: 60–300 s after an open failure, 30–150 s after an update failure, 120 s when no CPU sensor exists and 60 s when CPU sensors exist but no temperature/power selection is usable; a later successful pass recovers automatically. The same gate is consulted on every entry, so a sensor-less machine is not re-updated every second.
- The default UI never presents LHM values as the primary reading: the live line is explicitly labelled `LHM 对照` and the EC/Energy Meter labels are unchanged. When the user selects LHM as the primary display source, that same line flips to `EC/Energy Meter 对照（风扇控制/保护真值）` and shows the original EC temperature and Energy Meter power, so the control truth stays visible. Demo mode shows `LHM 对照：演示模式不采集` instead of placeholder `--` values, and never initializes LHM. Users can explicitly opt in to LHM as the primary display source; see the next section. Selecting LHM never changes the control fields. The separate GPU-only LHM reader likewise never changes the control fields.

Third-party dependency: `LibreHardwareMonitorLib` **0.9.7-pre717** (MPL-2.0, https://github.com/LibreHardwareMonitor/LibreHardwareMonitor), restored from nuget.org. It pulls further packages that also ship in the App and Guardian output; the authoritative inventory with licences lives in [THIRD-PARTY-NOTICES.md](../THIRD-PARTY-NOTICES.md) (copied into the release payload as `docs/THIRD-PARTY-NOTICES.md`). Because that package requires `System.Management >= 10.0.10`, the Hardware project pins `System.Management` 10.0.10 (previously 9.0.10). LHM and PawnIO are optional at runtime: without them the app builds, starts and logs `LhmStatus` explaining the missing cross-check. This dependency is read-only telemetry only; it does not change fan control.

## CPU display source setting (display only)

The primary CPU temperature/power shown to the user is selectable, but the selection is a presentation concern only. It is implemented in `MiniProToolkit.Core/CpuDisplaySourceSettings.cs` (`CpuDisplaySource`, `CpuDisplaySourceSettings`, `CpuDisplaySourceSettingsStore`, `CpuDisplaySourceSelector`).

| Setting | Values | Default |
| --- | --- | --- |
| `CpuDisplaySource` | `EcEnergyMeter = 0`, `LibreHardwareMonitor = 1` | `EcEnergyMeter` (EC temperature + Windows Energy Meter power) |

Persistence: `%LOCALAPPDATA%\MiniProToolkit\display-source.json`, schema version 1, written atomically through a temporary file. A missing file, a missing `source` field or a missing `version` field is read with the current schema and yields the compatible default without a warning; an unknown enum name/number, an out-of-range version or unreadable/corrupt JSON yields the default plus a warning that is logged and shown in the main window. The startup warning stays merged into the display-source status line across sampling frames (it is not cleared by the first refresh) until the next successful save. Loading never throws, so a bad file cannot block startup.

UI: main window button `显示源设置` opens `DisplaySourceSettingsWindow` (same modal owner/save/cancel pattern as the taskbar settings). Saving writes the file first and only then switches the running display; a failed save reports an error and leaves the active source unchanged. Cancelling changes nothing.

Display semantics:

- `EC/Energy Meter` (default): `DisplayCpuTemperatureC`/`DisplayCpuPackagePowerWatts` equal `CpuTemperatureC`/`CpuPackagePowerWatts`. The `LHM 对照` line keeps showing the comparison values.
- `LHM`: each metric is resolved independently. A usable LHM temperature is shown instead of the EC value, and a usable LHM power is shown instead of the Energy Meter value. When a metric is missing, invalid (including LHM's driver-less `0.0 °C`/`0 W` placeholders) or LHM never sampled, that metric alone falls back to the EC/Energy Meter value. `DisplayTemperatureFromLhm`/`DisplayPowerFromLhm` record which metric actually used LHM, and `DisplaySourceStatus` carries a short per-metric fallback notice such as `LHM 不可用，已回退系统源（温度用 EC，功耗用 Energy Meter）；请以管理员运行并确认 PawnIO/传感器可用。` In this mode the main window's cross-check line shows `EC/Energy Meter 对照（风扇控制/保护真值）: <EC °C> / <Energy Meter W>` instead of calling LHM the comparison.
- Switching the source re-projects the in-memory 2-minute trend rows via `CpuDisplaySourceSelector.Reproject` (pure: no hardware read, no disk write, no control pass) and repaints the chart, so the curve never mixes old and new sources for the full window; the chart legend states which source the curves follow. Already written history rows are never rewritten.
- Consumers: main window labels (`CPU 温度（LHM/EC）`, `CPU 封装功耗（LHM/Energy Meter，非整机）`), the taskbar status items and tooltip, the live 2-minute trend, and the display fields of every new telemetry row. The history table includes `EC °C`, `显示 °C`, `Energy Meter W`, `显示功耗 W`, `显示源` and `显示提示` columns; old records without display fields fall back to `CpuTemperatureC`/`CpuPackagePowerWatts` when charted.
- `CpuDisplaySourceSelector.Apply` only writes the new display properties of `HardwareSnapshot` through a `with` expression. `CpuTemperatureC` (EC) and `CpuPackagePowerWatts` (Energy Meter) are copied unchanged.

Control isolation: `FanCurveController`, `FanCurveEngine` (including the 90 °C emergency duty), `FixedRpmControlSession`, `GuardianLeasedFanTarget` and every `SetFanDuty`/`RestoreAutomatic`/EC write keep reading `HardwareSnapshot.CpuTemperatureC` and the existing control state. The display setting is never consulted on a write path, so choosing LHM cannot change fan duty, protection thresholds or the Guardian lease. In demo mode the setting is honoured for labels only; no LHM instance is created.

## Taskbar status window

The taskbar status is a borderless, non-activating topmost WPF overlay positioned inside the Windows appbar rectangle for the one supported display. It is deliberately not reparented into Explorer, avoiding the blank/unpainted WPF child behavior observed when the elevated app crosses the Explorer integrity boundary. Per-monitor DPI awareness is declared process-wide in `src/MiniProToolkit.App/app.manifest` (`dpiAware=true/pm` for legacy Windows, `dpiAwareness=PerMonitorV2, PerMonitor` for Windows 10 1607+), so `GetDpiForWindow`/`GetDpiForMonitor` report the real current-display scale instead of a virtualized one; no runtime `SetProcessDpiAwarenessContext` call is made because the manifest already fixes the process context. Current-display DPI, automatic-hide layout and Explorer restart remain target-machine checks; per-display customization and cross-screen behavior are outside the product scope. CPU package power is one configurable status item and is enabled by default. The temperature/power items follow the selected display source (EC/Energy Meter by default, LHM after opting in); the tooltip lists both the displayed source and the original EC/Energy Meter values, while menu enable/disable logic keeps using the EC temperature. Placement and direction are computed by the pure `MiniProToolkit.Core.TaskbarOverlayLayout` helper from the rectangle reported by `SHAppBarMessage(ABM_GETTASKBARPOS)`: the real appbar edge decides the orientation (left/right taskbar → vertical layout, top/bottom → horizontal), and the saved `Vertical` preference is only a fallback for when the edge cannot be read. An empty or inverted appbar rectangle (auto-hidden taskbar, shell restart) makes the overlay `Hide()` itself instead of staying at stale coordinates, and the next valid rectangle `Show()`s it again without activating; no control logic runs while it is hidden. The overlay is also event-driven: the main window registers `RegisterWindowMessage("TaskbarCreated")` and handles that token plus `WM_DISPLAYCHANGE`/`WM_DPICHANGED`/`WM_SETTINGCHANGE` (wParam 0) in the existing `HwndSource` hook, and every notification is coalesced into a single `Dispatcher.BeginInvoke` pass that re-enumerates the taskbars only after a shell restart and otherwise just repositions the existing windows. This shell enumeration is implementation detail, not secondary-taskbar or multi-display product support. The hook is attached once and removed together with the `TaskbarCreated` token on teardown (`EnsureWindowHook`/`ReleaseWindowHook`); the decision table and the interval/coalescing bookkeeping are pure `MiniProToolkit.Core.TaskbarRefreshPolicy` (`TaskbarRefreshTrigger`, `TaskbarRefreshScheduler`), so the message classification and the one-refresh-per-interval rule are unit-tested. The 1 s periodic pass still refreshes the displayed values; only the mount/placement work moved to events. The taskbar right-click menu also offers `任务栏显示项…`, which calls the same `TaskbarSettingsClick` entry point as the main window button; the single-click-open and the control gating are unchanged. A double click is deliberately the same gesture as a single click (TrafficMonitor habit): it raises the existing `OpenRequested` once and nothing else. `MouseLeftButtonUp` filters on `ClickCount` through the pure `MiniProToolkit.Core.TaskbarClickGesture.RequestsOpen`, so only the first release of a multi-click sequence opens the main window and the repeat pairs of a double/triple click are dropped instead of showing/activating it twice; no second gesture, hardware action, timer or throttled single click is introduced, and the right-click menu plus its enable/disable gating stay untouched. The rule is unit-tested (`TaskbarClickGestureTests`), the real double-click on a live taskbar is not yet accepted on a target machine.

## OSD popup (display only)

The structured popup lives in `src/MiniProToolkit.App/OsdWindow.xaml(.cs)`; the settings/appearance editor lives in `src/MiniProToolkit.App/OsdSettingsWindow.xaml(.cs)`; the pure message/theme/appearance/settings models live in `src/MiniProToolkit.Core/OsdMessage.cs`, `OsdTheme.cs`, `OsdAppearance.cs` and `OsdPreferences.cs`. It targets the one supported display. Fixed built-in glyph icons and event factories exist; the implemented 16-event whitelist/template management and v3 preferences are described below, with manual target-machine UI acceptance still pending. Multi-display, per-display and cross-screen behavior are historical/product-plan references outside the current scope.

| Setting | Values | Default |
| --- | --- | --- |
| on/off (`enabled`) | `true` / `false` | `true` |
| theme (`theme`) | `Default`, `Light`, `Dark` | `Default` |
| foreground color (`foregroundColor`) | `null` (follow theme) or any strict `#RRGGBB`/`#AARRGGBB` (the `OsdColorCatalog` presets are quick picks only) | `null` |
| background color (`backgroundColor`) | `null` (follow theme) or any strict `#RRGGBB`/`#AARRGGBB` (the `OsdColorCatalog` presets are quick picks only) | `null` |
| background opacity (`backgroundOpacity`) | `0.2` – `1.0` | `1.0` |
| font size (`fontSize`) | `null` (follow theme) or `12` – `40` | `null` (22 pt title / 15 pt body) |
| font family (`fontFamily`) | `null` (follow theme) or a plain family name, 1–64 chars of letters/digits/space/`- _ . + ( ) '` | `null` (= theme family `Segoe UI`) |
| placement (`placement`) | `TopLeft` … `BottomRight` (9 slots) | `TopCenter` |

UI entry points: the tray menu keeps `OSD 提示` (toggle) and `OSD 主题` (preset); the main window button `OSD 设置` and the tray item `OSD 外观设置…` open the appearance editor (foreground/background color preset dropdown **plus a free-text hex field**, opacity slider, font-size dropdown, **free-text font family field**, placement dropdown, plus `恢复默认` / `取消` / `保存`). Colors and the font family are user text: the hex field is capped at `OsdColorRules.MaxInputLength` (9 chars) and must match `#RRGGBB`/`#AARRGGBB` exactly, the font field is capped at `OsdFontFamilyRules.MaxLength` (64 chars) and must be a plain family name, and both are validated on every keystroke (inline error, `保存` disabled). The dropdowns stay as quick picks (`OsdColorCatalog`, `OsdFontSizeCatalog`, `OsdPlacementCatalog`) and simply fill the text field; an empty field means "follow theme". A valid value that is not in a catalog (for example from a hand-edited file) is shown as an extra `自定义` entry, so opening and saving the editor never drops it. A well-formed but not-installed font name is accepted, flagged as "本机未检测到，将回退默认字体", and resolved to `Segoe UI` when the popup is created.

Persistence: `%LOCALAPPDATA%\MiniProToolkit\osd.json`, schema version 3 (version 1/2 files still load; missing fields keep compatible defaults), atomic temporary-file replacement. A missing file, a missing field or a missing `version` reads as the compatible default with no warning, so a version-1 file (on/off switch and theme only) keeps the first-version colors, 22/15 pt sizes, opacity 1 and top-center position. Validation is field by field and never throws:

- unknown/non-preset theme → theme resets to `Default`, the switch and appearance are kept (warning);
- color that is not strictly `#RRGGBB`/`#AARRGGBB` (wrong length, non-hex, no leading `#`) → that color resets to "follow theme" (warning);
- `fontFamily` that is not a plain family name (path separator, drive colon, `#`, `%`, comma, quote, control char) or longer than 64 chars → resets to "follow theme family" (warning); a well-formed name that is simply not installed is kept in the file and resolved to `Segoe UI` by `OsdFontResolver` when the popup is built (never an exception, never a font file/URI load);
- `fontSize` outside `12`–`40` (or NaN/∞) → resets to "follow theme" (warning);
- `backgroundOpacity` outside `0.2`–`1.0` → resets to `1.0` (warning);
- unknown placement name or out-of-range number → resets to `TopCenter` (warning);
- wrong JSON types, unreadable/corrupt JSON or an unsupported version → the whole default with a warning.

`OsdPreferencesStore.Save` sanitizes the same way before writing, so an invalid programmatic value can never be persisted and re-read as "corrupt". Loading never throws, so a bad file cannot block startup or fan control.

Theme semantics: `Default` reproduces the first-version look for `Info` messages (semi-transparent `#D9212121` chip, white 22 pt title, no accent bar). `Light` uses dark text on a near-opaque white chip, `Dark` is an opaque dark chip. Success/warning/error always keep their own accent bar (the preset only changes their contrast).

Appearance precedence (`OsdThemeCatalog.Resolve(preset, appearance)`): the preset supplies the palette, font family and severity accents; the user background replaces the chip background of every severity (the accent bar and its color stay per-severity, so success/warning/error remain distinguishable); the user foreground replaces the body color and the neutral `Info` title color; the user font size sets the title size and derives the body size with the preset ratio (22/15 by default); the user font family replaces the preset family (the name is resolved against the installed fonts by `OsdFontResolver`, unknown names fall back to `Segoe UI`); the opacity multiplies the alpha of whichever background was used, and an opacity of `1` returns the theme color byte-identically. A `null`/all-default appearance returns exactly `Resolve(preset)`, which is why old files are pixel-identical. Position and font size are independent of the theme: switching the preset never resets them.

Application: `MainWindow.ApplyOsdAppearance` resolves preset + appearance and calls `OsdWindow.ApplyTheme` / `OsdWindow.ApplyPlacement` on the UI thread only, marshalling and swallowing/logging any failure (the previous appearance is kept). `OsdWindow.PositionOnCursorScreen` uses `OsdPlacementLayout.Compute` (pure, tested) with the existing cursor-monitor work area and per-monitor scale: the top row keeps the legacy 20% offset so `TopCenter` is the first-version position, the other slots use a 16 DIP edge margin, and the result is clamped inside the work area. The cursor-monitor/per-monitor naming describes the implementation; it does not expand the product beyond the one supported display or add cross-screen acceptance.

Persistence and font resolution never load a font file: only installed family names are matched (`System.Windows.Media.Fonts.SystemFontFamilies`, cached once), so a stored string can never address a path or URI.

Isolation: every OSD setting is presentation only. Loading or changing them reads and writes one small JSON file and repaints the popup; no EC/WMI/Guardian call is made or skipped, no sampling pass or control pass is triggered, and the on/off switch only silences the popup. Demo mode creates no hardware object and can still switch themes and appearance.

### OSD templates and new fan-control code status

`Core/OsdEventTemplates.cs` implements a 16-event key whitelist, v3 preferences and management UI. Safety events and Warning/Error preserve original title/body/icon/severity and cannot shorten duration. Overrides are bounded plain/redacted display data, not resources or executable content. This is implemented and targeted-Core covered, not target-machine accepted.

Curve `FanCurvePoint.TargetRpm` is all-points optional, with independent bounded add/reclaim tracking, temperature/ramp duty-floor priority, mutual exclusion with legacy `RpmFeedback`, emergency 100% and editor/config round trip. Incompatible startup calibration strips only TargetRpm, preserves temperature/Duty safety points and warns; ApplyCurveSettings validates actual calibration before saving. Automatic sampling code uses 40→100 step10, starts 0<T<65°C and stays 0<T<70°C (70 abort/restores), 3 s settle + median of 5 unique stable samples (range≤150 RPM), 30 s/point, 4 min total. Cancellation/lease/Guardian/bad-sample failure stops calibration writes; successful EC-auto restoration precedes draft replacement and Save precedes application; demo disabled. Automatic calibration still requires hardware acceptance. Tracking has a limited 20 s success on the earlier Core `FF335A8B…` snapshot, not a mode-fix fan retest or full thermal/fault acceptance. Current mode-fix Release/build/install evidence is described in [release-packaging.md](release-packaging.md); this documentation-only round does not rebuild or change binaries.

## Read-only CPU frequency display

CPU frequency is a display-only metric: `MiniProToolkit.Hardware/CpuFrequencyReader.cs` reads `Processor Information\% Processor Performance` (falling back to `Processor\% Processor Performance`) and converts it to MHz with the base clock from `HKLM\HARDWARE\DESCRIPTION\System\CentralProcessor\0\~MHz`; the pure state/enum types live in `MiniProToolkit.Core/CpuFrequency.cs`. The first sample only establishes a baseline, and `0`/NaN/out-of-range readings become unknown (`-- MHz`) rather than `0 MHz`. It runs inside the existing one-second background sampling pass (never on the UI thread), opens no driver, writes no MSR/EC, and is disposed with the sampling lifetime; a dispose/rebuild failure only degrades the frequency row to unknown with a short status. Nothing on the control path (`FanCurveEngine`/`FanCurveController`, `FixedRpmControlSession`, the 90 °C latch, `GuardianLeasedFanTarget`) reads it. It is taskbar item `CpuFrequency` (enum value 11, not added to existing settings automatically) and a main-window `CPU 频率` line; the live trend chart gains no new axis. Windows efficiency-class grouped frequency is also implemented (`Core/CpuClassFrequency.cs`, `Hardware/CpuClassFrequencyReader.cs`) and connected to MainWindow/JSONL/history. It maps CPU-set EfficiencyClass/group/logical-index, not guessed Intel P/E; homogeneous topology is NotApplicable. The 256-counter bound rejects rather than truncates oversized heterogeneous topology. Absolute `Processor Information\\Processor Frequency` MHz is not effective clock. CSV stays 31 columns; real counter accuracy is not target-machine accepted.

## Read-only GPU temperature (optional LHM GPU group)

`MiniProToolkit.Hardware/LibreHardwareMonitorGpuSensor.cs` owns a **second, GPU-only** LibreHardwareMonitor `Computer` (independent from the CPU cross-check reader): `IsGpuEnabled = true` while CPU/MSR, motherboard/SuperIO, storage/NVMe, network, memory, controller, battery, PSU and power-monitor stay `false`, so board, NVMe and network sensors are never enumerated. Candidates are filtered by LHM sensor category (`Temperature` only) and by GPU hardware type (`GpuNvidia`/`GpuAmd`/`GpuIntel`); the selection prefers `GPU Core`/`GPU Temperature` and drops `null`/NaN/infinite, 0 °C and out-of-range values. The reader never throws, never installs PawnIO, never writes MSR/EC and is not part of any control path: `CpuTemperatureC` (EC) remains the only temperature the curve, the fixed-RPM loop, the 90 °C protection and the Guardian lease read, and the value does not feed `CpuDisplaySource` either.

It runs inside the existing one-second background sampling pass (never on the UI thread, one `Read()` per pass), and every sample fills `GpuTemperatureC` / `GpuSensorName` / `GpuSensorStatus` on `HardwareSnapshot` and the telemetry record. A successful sample is cached for `MinimumSampleInterval` (5 s) because GPU polling is more expensive than the CPU pass; failures reuse the shared `LhmRetryPolicy` backoff (base delay × consecutive failures, capped 5×), 120 s when no GPU sensor exists and 60 s when GPU sensors exist but no usable temperature is selectable. The instance is created in the `MainWindow` constructor (demo mode keeps the field `null`), rebuilt by the background pass after a resume or an aborted exit (both set a reinitialize flag; `Dispose()` is final and there is no re-open API) and released by the ordered exit's `ReleaseOptionalReaders`. The telemetry fields are JSON-only: the CSV header and column count are unchanged, so no schema archive is triggered and old JSONL rows deserialize with nulls. UI surface: one main-window line `GPU（LHM 只读，不参与控制）` that degrades to `--` plus the redacted reader state, a read-only GPU column (cell tooltip = sensor name) and a `GPU 传感器/状态` column in the history sample table, and the appended taskbar item `GpuTemperature` (enum value 12, never injected into existing settings files). Demo mode shows `演示模式不采集` instead of placeholder values. Release read-only probing observed GPU 35°C on its recorded snapshot, without accuracy acceptance. An independent `LibreHardwareMonitorAuxTemperatureSensor` now enables Motherboard/Storage only, with pure `AuxTemperatureSelector` and MainWindow/JSONL/history wiring. Either valid group keeps a 5 s cadence; both missing back off 5–320 s. Unknown is null, not zero; CSV stays 31 columns. This independent reader does not change the GPU reader's group flags and never feeds EC/fan/Guardian or `CpuDisplaySource`; Release probing observed Storage 38°C while board stayed unknown; accuracy and complete target-machine acceptance remain open.

## Global hotkeys (configurable)

The app's own Windows global hotkeys (silence/balance/performance modes, EC automatic, full speed) are rebindable since this round. Defaults stay `Ctrl+Alt+1/2/3/A/F`. `MiniProToolkit.Core/HotkeySettings.cs` owns the rules and `HotkeySettingsStore` persists them in `%LOCALAPPDATA%\MiniProToolkit\hotkeys.json` (schema v1: `version` + `bindings[{action, modifiers, key}]`): the key whitelist is `A-Z`/`0-9`/`F1-F12`, modifiers are restricted to Ctrl/Alt/Shift/Win and must contain at least one of Ctrl/Alt/Win, shell-reserved combinations (`Alt+F4`, `Win+L/D/E/R/S`) and duplicate combinations across actions are rejected, and saving refuses an invalid set instead of writing it. Loading never throws: a missing file, a missing field, an unknown action, an unsupported key/modifier or an out-of-date version falls back **per action** to the shipped default (with a warning), and an in-file conflict keeps the first action and defaults the later one - only an unresolvable file resets everything to the defaults.

Registration lives in `MainWindow`: one `RegisterHotKey` call per action (id = enum value + 1), so a combination already owned by another process only degrades that single action (the rest keep working) and the failure summary is log-safe (action label, gesture, fixed reason - never a path or a command line). A rebind unregisters only the app's own ids and re-registers them; the shared message hook (`TaskbarCreated`, display changes) stays attached, the ordered shutdown still unregisters everything in `UiTeardown`, and a cancelled exit re-registers what is missing. The settings entry is the existing taskbar dialog ("任务栏与快捷键设置"), which submits display settings and hotkeys together but persists them to their two files separately. All of this is Core/directed-test covered and **not** target-machine accepted (real key capture, immediate rebind, re-register after a failed exit); vendor Fn keys and touchpad control remain excluded and are unrelated to these hotkeys.

## Command line, named-pipe IPC and single instance

The app is the only hardware owner on the machine. `MiniProToolkit.Core/ToolkitSingleInstanceLock.cs` wraps a `Global\MiniProToolkit.Instance.v1` mutex (machine-wide, visible across logon sessions and users, not `Local\`); the first process acquires it and owns the command pipe, and a second launch never creates a second window or a second hardware owner:

- mutex could not be created or opened (state `Unavailable`): fail closed with exit code 7 and no window, no hardware handle, no relayed command. Creating an object in `Global\` needs `SeCreateGlobalPrivilege`; the app manifest requests `requireAdministrator`, so every real launch holds it, and a non-elevated host fails closed instead of guessing;
- mutex already owned by another process: the second process asks the running instance to `activate` (restore + activate the main window) over the pipe and exits with 0, or with 8 if that request failed. Because the pipe is per-user (`PipeOptions.CurrentUserOnly`) another user/session cannot reach the first instance's server, so that launch ends with 8 (or 7 when the lock cannot be created) and never starts second-instance hardware control.

Scripted commands are split into three pure pieces plus two host adapters:

| Layer | File | Responsibility |
| --- | --- | --- |
| Parser | `MiniProToolkit.Core/ToolkitCommandLine.cs` | Whitelisted actions `status` / `apply-profile` / `set-mode` / `restore-automatic` / `help` / `activate`, host flags `--quiet` / `--demo` / `--startup`, structured error codes, log-safe text that never echoes raw arguments or values |
| Protocol | `MiniProToolkit.Core/ToolkitCommandIpc.cs` | Fixed version string, strict JSON (unknown fields/actions, duplicate or missing confirmation rejected), 4-byte length framing, per-message byte caps, one request per connection, a well-formed `requestId` mandatory for the three write actions |
| Host decision | `MiniProToolkit.Core/ToolkitCommandOutcome.cs` | Disposition + exit codes: 0 success/usage/windowed launch, 2 command line rejected, 4 no accepting instance (not running, IPC unavailable, connect timeout, protocol mismatch), 5 instance refused or execution failed, 6 instance timed out, 7 instance lock unavailable, 8 already running but activation failed. `RelayPending = -1` is an internal sentinel that is never returned to a shell |
| Client | `MiniProToolkit.App/AppCommandPipeClient.cs` | Connects to the per-user pipe (`PipeOptions.CurrentUserOnly`), bounded connect/read/write/execute timeouts, maps failures onto the exit codes above |
| Server | `MiniProToolkit.App/AppCommandPipeServer.cs` | Accepts on the UI thread and calls the existing `ExecuteAsync` / `ApplyProfileAsync` / `RestoreAutomaticAsync`, so `_gate`, Guardian availability/lease checks, the demo guard and exit-time EC restore all apply unchanged. Write commands are deduplicated through `ToolkitCommandRequestCache` (bounded in-memory LRU, 32 entries / 60 s, keyed by requestId + action): the id is recorded before dispatch, so a duplicate is answered (`executed = false`, or a timeout-shaped "already in flight, re-check with `status`") and never reaches `MainWindow` a second time. Nothing is persisted, so a restart clears it and no path or command line is ever stored |

The command process itself performs no WMI/EC/fan write and never opens a second hardware instance; when no instance answers it exits with 4. Command paths show no MessageBox; `--quiet` writes only stdout plus `%LOCALAPPDATA%\MiniProToolkit\miniprotoolkit.log` with a safety summary (action name, status, exit code). An optional `--request-id=<32 hex>` (never echoed, not part of any log-safe summary) is generated per launch when omitted, so the existing one-connection-one-request CLI stays compatible; a client that lost the answer after the request was on the wire still exits with 6 and is told to re-check with `status`. There is no cross-session/cross-user audit: the replay cache is per process and a command from another user cannot reach the first instance's per-user pipe. The default client answer budget is `ServerWorstCaseMilliseconds` (40 s: 10 s to start the handler plus 30 s bounded execution) + 5 s = **45 s**, deliberately longer than the server's worst case so a slow-but-successful command is never reported as "failed"; shrinking it would turn a real success into exit code 6 while the EC has already changed.

## Profile automation process conditions

`MiniProToolkit.Core/ProfileAutomation.cs` matches the rules' process conditions; `MiniProToolkit.App/ProfileAutomationProcessSampler.cs` supplies the transient process inventory on the background automation tick (5 s).

| Condition | Field | Rules |
| --- | --- | --- |
| process name | `ProcessName` | Normalised name, matched case-insensitively; always required for process-triggered rules |
| full executable path | `ProcessPath` | Drive-letter or UNC **full** path only (relative paths and wildcards are rejected); compared with the sampled `MainModule.FileName` |
| command-line substring | `ProcessCommandLine` | Case-insensitive `Contains` over the sampled `Win32_Process.CommandLine` |
| command-line regex | `ProcessCommandLineRegex` | Case-insensitive `Regex` with a 200 ms match timeout (compiled patterns cached, bounded cache); substring and regex are mutually exclusive; an invalid pattern is rejected on save |

Behaviour and safety: the sampler only reads the expensive values when at least one rule declares them (`needsExecutablePath` / `needsCommandLine`), caches command lines in memory for at most 256 processes, and never writes a command line to logs, diagnostics, telemetry or OSD text - failures surface as `CommandLineUnavailable` (denied/unreadable), `CommandLineMismatch` or `InvalidCommandLinePattern`, and a rule that cannot read the command line is skipped instead of matching. Matching only decides whether a profile is a candidate; applying it still goes through the same serialized gate, profile validation and rollback path as a manual apply, and automation stays opt-in (default off).

Runtime status board: `MiniProToolkit.Core/ProfileAutomationStatus.cs` (`ProfileAutomationStatusBoard`, `ProfileAutomationRuleStatus`, `ProfileAutomationRuleOutcome`) counts evaluations, matches, skips and rejections per rule and keeps the last evaluation/match timestamps plus a fixed summary line. It lives in `MainWindow` memory only - it is never persisted, never written to history, diagnostics or telemetry, and its closed outcome codes carry no process path, command line or command-line pattern - and it is rendered by `ProfileAutomationWindow`. Resetting the automation settings or editing the rule list resets the board. Unit-tested (`ProfileAutomationStatusTests`) but not exercised against a real process tree.

## Shutdown sequence

`MiniProToolkit.Core/ShutdownRecovery.cs` (`ShutdownSequence`, `ShutdownPhase`, `ShutdownFailureAction`) makes exit ordering explicit: `ControlRecovery` (stop timers/power notifications, wait for the sampling gate, restore EC automatic and clean the lease) → `HardwareRelease` (telemetry recorder and `PowerSwitchHardware` released) → `UiTeardown` (tray, taskbar windows, OSD, hotkeys) → `Completed`. The phase only advances monotonically, so a late or repeated call cannot move the exit back. A failure before `HardwareRelease` resumes the session; a failure afterwards finishes the exit without resuming sampling, because the hardware handle is final and there is no re-open API. The application wires the phases in `MainWindow`'s exit path and re-registers hotkeys only when the exit was cancelled before hardware release.

Exit *requests* are serialized by `MiniProToolkit.Core/ExitRequestGate.cs` (`ExitRequestGate`, `ExitRequestSource`, `ExitFailureNotice`): only one exit sequence may run at a time (a concurrent tray/installer request is refused, never a nested `Close`/`OnClosing`), the installer stop signal (`Set` on `Local\MiniProToolkit.Shutdown`, waited with `executeOnlyOnce: false`) stays armed across a failed exit because the latch is simply re-armed on resume, and a signal-driven failure is logged instead of prompting (`ShowDialog` only for user requests that saw no shutdown signal). A signal that races a running exit is remembered and retried once after a failed exit; teardown disarms the gate first, then unregisters the wait and only then disposes the event handle.

## Curve status, emergency OSD and JSON-only telemetry fields

`MiniProToolkit.Core/FanCurveStatus.cs` (`FanCurveStatusKind`, `FanCurveStatusFormatter`) turns a control pass into a single status line: `Normal`, `Warning`, `PreEmergency`, `CurveEmergency`, `SensorInvalid`, `GuardianUnavailable`, `RecoveryPending`, `LeaseInvalid` and `ApplyFailed`, each with the Core-provided reason. `MainWindow.DisplayCurveState` renders it; the curve 90 °C emergency has its own OSD event (`osd-curve-emergency`, in `OsdNotifications.cs`) that is deliberately separate from the fixed-RPM latch event (`osd-emergency`), because a curve emergency is not latched and releases as soon as the temperature falls back.

`HardwareTelemetryRecord.CurveStatus` / `CurveReason` (plus the CPU frequency fields) are **JSON-only**: they are written to `telemetry.jsonl`, keep the CSV header/columns unchanged (so no CSV schema archive is triggered), and older rows deserialize with `null`. Neither field carries paths, command lines or adapter details.

## Control and recovery scheduling

Hardware reads are read-only. The app explicitly applies `FixedRpmControlSession` after sampling, using a one-second control cadence and a monotonic minimum feedback interval; taskbar refresh settings only affect presentation. Invalid/stale samples, lost leases, Guardian stop and feedback failures stop fixed-RPM writes and request EC automatic. Recovery failures retry restoration without resuming duty correction. Fault context stays visible after successful automatic recovery. Curve disable failures also stop output and retain recovery state. Incompatible CSV headers are archived before new rows are appended. See [fan-control-hardening.md](fan-control-hardening.md) for behavior, verification and limitations.

## Duty/RPM calibration

`FanCalibrationStore` loads the single version 1 calibration set from `%LOCALAPPDATA%\\MiniProToolkit\\fan-calibration.json`. Invalid files fall back to the default measured table with a visible warning, while strict imports reject invalid files. The editor provides point editing, a preview, import/export and reset. Calibration must cover 40–100% duty and is injected into both the fixed-RPM target resolver and bounded feedback controller. Applying a saved calibration replaces these calculators under the hardware lock without calling WMI; active manual control or pending recovery blocks the update. Temporary-file replacement and a `.bak` copy preserve the previous saved configuration. Multiple calibration sets are outside the current single-fan scope and are not a backlog item. See [fan-calibration.md](fan-calibration.md).

## Hardware contract

- `GetPowerMode` / `SetPowerMode`: Balance `0`, Performance `1`, Silence `2`.
- `GetHwTemp(HwTempType=1)`: CPU temperature in the low byte.
- `GetFanControl(FanNumber=1)`: packed RPM, low 16 bits Fan1; any high-word Fan2/RPM value is retained only as read-only compatibility data and is not selectable or controllable.
- `SetFanControl(FanNumber=1, FanDuty=0..100)`: manual duty.
- `SetFanControl(FanNumber=1, FanDuty=101)`: return control to EC automatic mode.

The MVP never writes fan control during startup. The UI can apply the safety curve only after the Guardian service is detected as running. The core engine/controller clamp duty to 40-100 percent, use 2 C hysteresis, limit normal changes to 10 percentage points per tick, send 100 percent immediately at 90 C, and request firmware automatic control for stale/invalid temperature or write failure. Every curve write goes through the curve lease gate (`MiniProToolkit.Core/FanCurveLeaseGate.cs`): the lease is published before the first WMI write and renewed after each completed one-second control pass, a missing/expired/foreign-owner lease blocks the write, and renewal is suspended while recovery is pending. The fixed-RPM 90 °C latch is a separate protection state: it keeps 100 % duty until an explicit EC-automatic restore, and ordinary faults (Guardian stopped, invalid lease, bad samples) do not clear it. The measured 20 percent point is only about 1200 RPM on this machine, while the firmware baseline is about 2080 RPM. `PowerSwitchHardware.Dispose` and `FanCurveController.Dispose` attempt to restore automatic control. The Guardian worker polls `%ProgramData%\\MiniProToolkit\\guardian-lease.json`, checks PID and process start time, restores `FanDuty=101` when the owner process dies or the heartbeat is stale, and then clears the lease with a compare-and-clear: PID, process start time, control mode and heartbeat must all still match the record it recovered, so a lease written by a restarted main app during recovery is never deleted by the stale cleanup. The compare-and-clear and the write are serialized across processes by a short-held `<lease>.lock` file (`FileMode.OpenOrCreate` + `FileShare.None`, bounded 300 ms wait, released before any WMI/EC call), so the app and the SYSTEM Guardian cannot interleave "compared, then deleted" with a new publish; if the lock cannot be taken, `WriteActive` fails closed without writing a lease and `ClearOwned` is a safe no-op that keeps the lease for the next Guardian poll. This is not a cross-process atomic hardware lock: the `FanCurveLeaseGate` decision is still the one lease read taken at the start of the pass. If restoration itself fails, the lease is retained for retry.

Default fan curve template (`FanCurveSettings.Default`): the curve nodes stay 45/40, 55/45, 65/55, 75/70, 85/85, 90/100 with the existing ramp-down points, and the template now also ships the conservative graded temperature tiers: `WarningTier = 70 C / 80 %` and `PreEmergencyTier = 82 C / 100 %` (`DefaultWarningTierTemperatureC`, `DefaultWarningTierDutyPercent`, `DefaultPreEmergencyTierTemperatureC`, `DefaultPreEmergencyTierDutyPercent`). Both tiers validate against that curve (the curve alone asks 62 % at 70 C and 80 % at 82 C, so the tiers can only add cooling), the fixed 90 C / 100 % emergency path is unchanged and still bypasses hysteresis and the per-tick duty ramp, and `RpmRateLimit` stays `null` because RPM/s limiting needs real fan feedback and remains opt-in (when it is enabled the window anchor is deliberately sticky: samples shorter than `MinimumSampleSeconds` only observe the fan and never move the anchor, so a burst of short samples cannot turn RPM jitter into a rate decision). This template is the single source for new profiles, the built-in `FanProfile.Defaults`, the curve editor "恢复默认" button and the store fallback when `fan-curve.json` is missing or unreadable. Config files written by older builds (version 2 without `warningTier`/`preEmergencyTier`/`rpmRateLimit`) still deserialize to `null` and therefore keep exactly the legacy curve-only behaviour; saving from the current build writes the optional fields only as the user configured them. Two further optional curve safety settings exist and are **default-off**: `RpmFeedback` (`FanCurveRpmFeedbackSettings`, a bounded feedback loop that can only raise duty: deadband, minimum expected RPM, stall ratio, per-step and cumulative duty corrections) and `LatchCurveEmergency` (latches the curve's 90 °C full-speed request until an explicit "restore EC automatic"). With both absent/false the curve behaves exactly like the legacy build; both are edited in the curve editor, validated on save, and only produce configuration - the editor never writes hardware.
